# 梦境织机（Dream Loom）模型与 Lua 开发交接

版本：设计规格 v1.0 · 2026-09-27。适用项目：奶龙打地鼠 Evoker Cue / Raidary Plan。

本文是自包含的交接文档。接手者不需要阅读原聊天记录。下文明确区分用户确定的需求、研究使用的简化规则、已复核的实验结果，以及尚未实现的功能。当前任务只编写文档，没有把求解器装入插件。

## 1. 产品目的与研究背景

用户玩治疗专精唤魔师，希望只在战术板上安排关键的“静滞”开启时间，再输入战斗结束时间，由插件补齐梦境吐息、溜溜球、必要的花和释放静滞的时间轴。

模型正式命名为 **梦境织机**，建议代码命名空间 `EC.DreamLoom`。它是战前离线排轴器：生成供玩家手动执行的计划，不是自动施法器，也不是根据每帧战斗状态自动重算的实时决策器。

用户最初希望每次静滞后存“喷喷球”，随后允许缺球时存“喷喷花”，又补充“喷球喷”也合法：第一个喷后不一定已有第二层，球的减冷却可以使第二个喷及时恢复。这一补充直接影响合法性判定，不能只检查静滞起手是否两层满。

需求演进中已确认：

- 整场溜溜球次数优先，统计手动施放和静滞复制的球；不是只让手动球次数最多。
- 同时追求绿喷次数，不能为了形式上满充能而整场不打喷。
- 组合偏好为喷喷球 > 喷球喷 > 喷喷花；提供强制喷喷球模式和允许替代组合的优化模式。
- 球尽量卡 CD，喷尽可能晚放，但都要服从次数、静滞时间和施法占用限制。
- 必须排出释放静滞，不可把“开启静滞”当成已经释放了复制技能。
- 用户希望知道绿喷浪费了多少秒，不能只给技能次数。
- 回溯是独立技能，此次模型不计算其冷却和施法占用，保留原标记。
- 最终输出要包含静滞内真正手动存进去的技能；早期“省略存储技能”的要求已被用户撤回。

本产品属于 Raidary Plan 战术板模块，后续用于更完整的 Raidary 一体式插件。原文尽量简单：`00:01 韶光逍珑 静滞`；兼容已有 MRT 时间、法术 ID、横杠和尖括号格式。

## 2. 术语和计数边界

| 标记 | 用户称呼 | 内部建议 key | 含义 |
|---|---|---|---|
| B | 喷、绿喷、梦境吐息 | `DREAM_BREATH` | 消耗自身充能的手动绿喷 |
| Y | 球、溜溜球 | `BALL` | 消耗自身冷却的手动球；此 key 为设计建议 |
| F | 花 | `FLOWER` | 本模型中的瞬发替代技能；此 key 为设计建议 |
| S | 静滞 | `STASIS` | 开始记录接下来的指定三次施法 |
| R | 释放静滞 | `RELEASE_STASIS` | 释放已记录的复制技能 |

“静滞内手动 B/Y”与静滞外手动 B/Y 一样，消耗自身充能或 CD，不能免费。“释放静滞”的复制技能才不消耗自身充能和 CD。

`manualBalls`：战斗内完成的手动球，包括存入静滞的球。

`copiedBalls`：在战斗内释放含球静滞产生的球。

`totalBalls = manualBalls + copiedBalls`，为主要目标。

`totalBreaths = manualBreaths + copiedBreaths`；每个成功释放的合法静滞贡献两个复制喷。所有波次必须释放时，最大化手动喷等价于最大化总喷。

战前 -5 秒的球只决定起手 CD，不计入战斗内次数，不输出到战术板。

## 3. 模型规则：不要擅自换成实际游戏机制

以下为研究规格，不是对任意版本、天赋、急速下实际技能机制的保证。第一版先按这套固定模型实现，真实施法时间、公共冷却、天赋修正应作为另一个机制版本接入。

### 3.1 绿喷

- 两层充能，每层恢复 30 秒，**依次恢复**。
- 开怪时两层全满。
- 每次手动喷占用 1 秒；研究中在施法开始时消耗充能、开始恢复，完成后计为一次有效施放。
- 每次球的 5 秒减 CD 若超过当前一层剩余时间，余量继续抵扣下一层。
- 两层均恢复满后剩下的减 CD 才叫溢出。

### 3.2 溜溜球

- 一层，CD 为 14 秒，每次施法占用 2 秒。
- 战前 -5 秒开始施放过一个，故战斗 t=0 时剩余 CD 为 9 秒。
- 研究约定：**CD 从施法开始算；减绿喷 CD 在球施法完成时生效。**用户给定了时长和起手 9 秒，精确触发时机属于研究约定，接入真实游戏前需验证。
- 例如 t=9 开始球，t=11 减喷 CD，下一球最早 t=23 开始。
- 球不改变自身冷却，不会因为复制球额外恢复一个手动球。

### 3.3 花

- 用户确认按无 CD、随时可用、瞬发 0 秒处理。
- 实际消耗精华，但本模型不追踪精华，不额外计算 GCD。
- 仅用于指定静滞组合的第三个技能，不生成无穷多次零时长花。
- 正式技能名称和法术 ID 未在研究中确认，不要猜测并写死。

### 3.4 静滞与存储

用户战术板上的静滞时间是**开启并开始存储**的时间，不是释放时间。

开启静滞本身在研究中占用 0 秒。之后三个技能必须紧接施放，中间不插入其他手动技能，也不主动等待。允许组合：

| 组合 | t=S 起的手动施法 | 存好时刻 C | 释放截止 |
|---|---|---|---|
| BBY，喷喷球 | B@[S,S+1)，B@[S+1,S+2)，Y@[S+2,S+4) | S+4 | C+30 |
| BYB，喷球喷 | B@[S,S+1)，Y@[S+1,S+3)，B@[S+3,S+4) | S+4 | C+30 |
| BBF，喷喷花 | B@[S,S+1)，B@[S+1,S+2)，F@S+2 | S+2 | C+30 |

**30 秒从第三个技能完成开始计算**，不是从按静滞开始算。

每个静滞必须在 `[C, min(C+30, 战斗结束)]` 内释放一次。释放按 0 秒处理，模型中立刻结算两个复制喷和一个复制球/花；复制球立刻减自身喷 5 秒 CD。

研究求解只在玩家空闲的动作边界允许按释放静滞，不假设可在读条中插入释放。释放可以和下一次手动施法在同一秒先后执行。若将来验证可读条中释放，应显式扩展动作模型，不能默默改变历史结果。

不能同时持有两份未释放的静滞，不可让未释放包跨到下一次开启。截止时刻允许恰好释放。实际玩家延迟安全余量默认 0，若 UI 提供“提前释放余量”，必须作为改变可行域的参数显示并重新求解。

原截图提示静滞 90 秒冷却，研究案例所有开启间隔均不少于 90 秒。求解器把开启时刻视为固定输入；可提供 `stasisCooldown=90` 的预校验，冷却起算和是否受其他机制影响仍需实机核验，不能拿这一截图扩展出未确认机制。

### 3.5 时间范围及其他技能

- 默认整秒离散：`tickSeconds=1`。所有研究参数和输入都在整秒网格。
- 手动技能只有在 `start + duration <= fightEnd` 时才能计数；允许恰在战斗结束完成。
- 非零时长手动技能不能重叠。B/Y 正常读条期间 CD 继续恢复。
- 回溯等既有其他技能仅作为保留标记，不占用本模型施法资源。这是明确简化，输出不应声称整张战术板所有技能已经过读条冲突检查。
- 用户曾要求 Excel 行与 Boss 时间轴 ±5 秒视觉对齐。这是排版要求，**不是允许任意把求解出的技能时刻移动 5 秒**。若将来要真正挪时刻，必须重放验证，或作为搜索的软目标。

## 4. 两种运行模式与确定的比较顺序

`STRICT_BBY`：所有静滞强制喷喷球。若无解，报告具体波次与冲突，不能自行换花。

`FLEX_TOTAL`：每波允许 BBY、BYB、BBF，先保证整场次数，再按组合偏好选。

为避免“球最多”与“喷喷球最高优先”口头表达产生歧义，第一版采用研究实际用过的排序，UI 应展示它：

1. 满足所有固定静滞和释放硬约束。
2. 最大化 `totalBalls`。
3. 最大化 `totalBreaths`。
4. FLEX 模式下最大化 BBY 波次数。
5. 再最大化 BYB 波次数，等价于在此层尽量少 BBF。
6. 同次数、同组合质量时，最小化所有手动球开始时间之和（整体尽量早打球）。
7. 再最大化手动喷开始时间之和（整体尽量晚打喷）。
8. 再最大化释放静滞时间之和。
9. 如仍相同，以固定动作序和事件序稳定选择，保证相同输入得到相同结果。

“球尽量卡 CD”不能替代第 2 步：眼前能按就按，可能占用下个静滞内的球，减少一次复制球。

不要把 BBY 偏好提前到总球次数之前。若产品以后需要“无论损失多少球都优先 BBY”的策略，应加独立模式，不更改 FLEX 的含义。强制 BBY 已提供这种确定选择。

### 4.1 什么叫最晚

“整张轴整体后移喷”与“每个喷都有一个可以独立取用的最晚时刻”不同。

本版返回一张共同可行的、按上述目标选择的时间轴。不能把每个喷单独算出的最晚时间拼起来，拼出的轴可能同时要求同一层充能。

本版第 7 步定义的是**喷开始时刻总和最大**，不是已证明每个喷都达到其单独上界。若以后要显示每次施法的可移动窗口，需锁定其他条件重求解，且注明这些窗口不一定可同时实现。

旧脚本在固定组合内用一个大整数加权分数：每球 `10^14`、每喷 `10^11`，手动球时间权重 `-10000`，喷和释放时间权重 `+1`。它在本案例可用，但喷与释放的末级偏好混在一起，不完全等于上述第 7、8 步逐级比较。生产版使用显式词典序元组，旧轴只作为计数和可行性回归样本，不强制每秒完全相同。

## 5. 充能计算：用“恢复债务”表示两层串行充能

这是实现的关键。令 `w` 为将所有缺失充能恢复到两层全满所需的总秒数：

```text
0 <= w <= 60
w = 0       两层满
0 < w <= 30 一层可用，另一层正在恢复
30 < w <= 60 零层可用，两层缺口依次恢复
```

因此手动喷的开始条件为 `w <= 30`，开始后 `w = w + 30`。不要错写成必须 `w == 0`，也不要把两个独立倒计时同时递减。

任意经过 `dt` 秒：

```lua
idle = math.max(0, dt - w) -- 此段两层全满，无法继续利用的自然恢复时间
w = math.max(0, w - dt)
y = math.max(0, y - dt)   -- 球剩余 CD
```

球减冷却：

```lua
effectiveCDR = math.min(5, w)
overflow = 5 - effectiveCDR
w = math.max(0, w - 5)
```

这会自然处理跨层结转。例如 `w=32` 时零层可用，球后 `w=27`，得到一层可用，下一层还需 27 秒；不能把超出第一层剩余 2 秒的 3 秒丢掉。

BYB 合法性示例：起手 `w=8` 且球可用。第一喷开始后 38，1 秒后 37；球读 2 秒后 35，再减 5 得 30；此刻第二喷恰好可用。因此“起手一层而非两层”也可能合法。

同样不要反过来要求 BBY 起手必须 `w=0`：例如 `w=1`，第一喷 1 秒后 `w=30`，第二喷仍合法。应逐事件检查，不用过强的启发式拒绝方案。

### 5.1 事件同秒的处理顺序

1. 推进自然恢复到当前时刻，结束上一段读条。
2. 结算已完成技能的效果和次数；球在这里减 CD。
3. 若第三个记录技能完成，生成静滞包和释放期限。
4. 可释放刚存好的或已有的静滞包，结算复制效果。
5. 到固定静滞开启时间则开启记录。
6. 开始当前规定或自由选择的手动技能，消费自身资源。

同一时刻要存一个有顺序的事件列表，不能用 `events[time] = event` 覆盖同秒的 S、B、F、R。

## 6. 推荐求解器：离散动态规划 + 独立重放验证

不要只写“卡 CD 贪心”或“按每波倒推两层”算法。释放时机、复制球减 CD、下一次静滞需求和战斗末尾共同影响最优结果。

### 6.1 第一阶段：可复现参考算法

对于本案例四波静滞，FLEX 一共 `3^4 = 81` 种组合，STRICT 只有一种。可枚举组合；每种组合建立固定施法片段，再用相同 DP 搜索所有自由时间。每个组合都找完后，用第 4 节的总排序选择结果。

不需要先开发高级通用优化器。先让这份参考实现通过全部验证，再优化运行速度。

### 6.2 输入预处理

1. 读取当前选中方案的草稿副本和本人身份，解析本人静滞开启锚点。
2. 输入并验证战斗结束时刻；不存在时不要猜成最后一条战术板事件。
3. 验证时间格式、重复锚点、顺序、负时间、结束越界、静滞间距和固定录入片段重叠。
4. 第一版要求输入尚未安排本人 B/Y/F/R。若发现已有安排，报告行号，提供明确的“作为固定约束”或“重新生成”流程；第一版未实现固定约束时应拒绝，不能默默覆盖用户行。
5. 保存原始行、注释、其他人的安排及独立技能，求解器只处理规范化事件。
6. 释放静滞识别优先于静滞，不能把“释放静滞”误当作开启锚点。

### 6.3 状态

固定组合下，对每个整数时刻 `t` 存储一个稀疏状态表：

```lua
state = {
    w = 0,                 -- 绿喷恢复债务，0..60
    y = 9,                 -- 球剩余 CD，0..14
    pendingWave = 0,        -- 未释放包所属波次；0 表示无包
    releaseDeadline = 0,   -- 无包为 0，有包为完成时刻+30
    -- 固定片段由组合表和 t 唯一确定；不用另存录入计数。
}
label = {
    score = {...},         -- 显式词典序目标，不用巨大浮点权重
    parent = nodeIndex,    -- 前驱链，避免每次复制整张轴
    action = {...},
}
```

静滞包的类型由 `pendingWave` 对应的组合查出，不要只存截止时间来猜是否含球。实际 key 至少包含能决定未来合法动作和效果的全部状态。

`dp[t][stateKey]` 只保留该**完全相同状态**下目标最好的路径。不同状态不能仅凭当前总球更多就丢弃；较少次数但资源更充足的路径可能后来胜出。

### 6.4 转移

在空闲状态允许以下动作。每个转移都要检查期间没有跳过固定施法开始、零时长花、下一次静滞开启或待释放截止事件。

| 动作 | 起手条件 | 开始时 | 推进时间 | 完成时 |
|---|---|---|---|---|
| WAIT | 非强制技能起手点 | 无 | 1 | 无 |
| B | `w<=30` | `w+=30` | 1 | 手动喷+1 |
| Y | `y==0` | `y=14` | 2 | `w=max(0,w-5)`，手动球+1 |
| F | 指定 BBF 第三步 | 无 | 0 | 存储完成 |
| R | 有包、未过期、玩家空闲 | 清空包 | 0 | 复制喷+2；含球则球+1且减喷CD |

强制片段中只能执行该片段规定的动作，不能等待或换招。Y 转移一次跨 2 秒，内部的第二秒不能再启动别的手动技能。固定 Y 的占用标记应与本次 Y 转移相容，而不是把它误当成冲突。

在第三个记录技能完成时创建静滞包。BBF 的 F 是一次性零时长事件，处理后要标记阶段已推进，避免反复存包形成零时间循环。

### 6.5 零时长闭包与终态

推荐把每个 `dp[t]` 的处理分成“完成固定零时长事件 → 枚举释放/不释放 → 非零时长动作”。释放后的状态只向“无包”方向变化，不能重复释放。

必须在过期判定之前允许 R：`t == deadline` 仍可释放；不释放的分支不能越过截止。释放后的状态必须真的加入待展开队列，不能遍历一个旧快照而漏掉它。

在 `t == fightEnd` 时不再开始非零时长技能，但先处理可能的零时长 R。接受的终态须所有固定波次已完整记录并释放，不能把未释放的包当成收益，也不能接受读条未结束的技能。

伪代码：

```text
best = nil
for pattern in allowedPatterns:
    fixed = compileMandatoryActions(pattern, anchors)
    dp[0][initialState] = initialLabel
    for t = 0 .. fightEnd:
        frontier = applyMandatoryZeroTimeEvents(dp[t], fixed, t)
        frontier = enumerateOptionalRelease(frontier, t)
        for state, label in frontier:
            if pending expired or next anchor conflicts: reject
            if t == fightEnd:
                if all waves completed and no pending: compare final
            else:
                for action in allowedActionsAt(t, fixed, state):
                    if fitsEndAndFixedBoundaries(action):
                        nextState = simulate(action)
                        relax(dp[nextTime], nextState, score, parent)
    compare pattern result with best
return independentlyVerified(best)
```

### 6.6 性能和正确性边界

- 精确求解的“最优”只针对所声明的离散网格、合法组合和机制版本。1 秒网格最优不是任意小数时间全局最优。
- Lua 使用稀疏 table、整数状态编码或可诊断字符串 key，前驱池存节点；不要整轴拷贝。
- 状态预算与耗时统计要进入结果；数值必须先实测再确定，不能宣称固定毫秒内一定完成。
- 游戏主线程需要分批工作。建议纯求解器 `Step(expansionBudget)` 返回进度，由 UI 以计时器驱动；每次切方案/改参数递增 generation token，旧结果不得写入新方案。
- 组合数随波次数指数增长。大输入可改为在静滞开始处分支 BBY/BYB/BBF、把录入阶段纳入 DP 状态，避免外层完全枚举；这属于性能优化，不改变规则。
- 若预算用尽，可返回已找到的可行解并标 `optimal=false`；不能把剪枝启发式结果或中断结果标成已证明最优。
- 第一版不使用“满充能立即打喷”剪枝，因为用户末级目标恰恰可能要求较晚喷。
- 独立验证器不能直接调用同一份转移函数自证；应按事件顺序另写充能队列或资源重放。

## 7. 浪费秒数：两类分别报告

### 7.1 满充能空转

自然经过的时间中，绿喷已经两层满而无法继续恢复的时间：

`fullChargeIdleSeconds += max(0, dt - w_before)`。

输出区间列表，连续区间可合并。两层串行恢复只计一个恢复时钟，不能把满两层期间乘 2。

### 7.2 球减冷却溢出

每次手动或复制球生效前，`overflow = max(0, 5 - w)`。

输出每次球生效时刻、手动/复制来源、有效减 CD 和溢出秒数。记录的是球**完成**时刻，而不是开始时刻。

### 7.3 总量与解释

可以显示 `recoveryOpportunityLost = fullChargeIdleSeconds + cdrOverflowSeconds`，但始终同时展示分项。此合计表示模型内未利用的恢复机会，不等于“按这些秒数除以 30 就能额外打几个喷”。空转可能是晚打喷的偏好或固定静滞条件造成的。

剩余恢复债务 `endingBreathDebt` 单独显示，不叫浪费。它表示结束时已消费但还没恢复的充能。

第一版仅统计浪费，不擅自把“浪费最少”加到次数或组合偏好之前；后续若增加节约冷却模式，应显式改变目标版本。

## 9. 历史案例与已复核结果

### 9.1 输入

```text
00:36 韶光逍珑 <静滞>
01:21 韶光逍珑 <回溯>
02:10 韶光逍珑 <静滞>

05:17 韶光逍珑 <静滞>

初始两层喷，球剩 9 秒。回溯保留但不参与求解。

研究保存了 81 种组合的整秒 DP 摘要，其中最高结果为总球 30、手动喷 18；在组合偏好下选四波全 BBY。

| 项目 | 四波 BBY 样本 |
|---|---:|
| 手动球 | 26 |
| 复制球 | 4 |
| 总球 | 30 |
| 手动喷 | 18 |
| 复制喷 | 8 |
| 总喷 | 26 |
| 满充能空转 | 46 秒 |
| 减 CD 溢出 | 15 秒 |
| 两类恢复机会损失合计 | 61 秒 |
| 结束恢复债务 | 59 秒 |

混用 BBY/BBF 的另一张历史轴可做到 28 手动球 + 2 复制球 = 30，但组合偏好较差；不能因手动球更多就认为它更优。允许 BYB 后也有同为 30 球、18 手动喷的解，BBY 偏好使最终仍选择四波 BBY。

这不是证明所有用户输入都应该全 BBY。换锚点或战斗结束时刻，BYB/BBF 可能改善总次数或恢复可行性。

本次文档整理重新运行了独立重放验证，确认保存样本的合法性、46/15 秒损失与计数；没有在本次重新遍历 81 组合。因此“30/18 的最优值”来自此前保存的穷举 DP 结果，接手实现仍应自己重新求解校验，不把文档当独立最优性证明。

|---|---|---|---|
| 00:36 | BBY | 00:40 | 01:10 |

### 9.3 资源守恒校验

本样本自然恢复有效时间 `392 - 46 = 346` 秒；30 个球减 CD 理论 150 秒，实际有效 `150 - 15 = 135` 秒。

`初始债务 0 + 18×30 - 346 - 135 = 59`，等于结束债务。复制喷不增加债务。这条守恒式是独立验证的重要断言。

{time:0:09} - 韶光逍珑 {spell:已验证的ID}
```

“球”单字作为自动全局子串别名可能误匹配其他技能或注释，第一版默认用完整俗称“溜溜球”和正式名；如提供单字别名，要求完整技能 token 匹配或用户自定义明确启用。中文标点、玩家名、MRT 链接继续走原归一化流程。

正式 ID 确認方法：用户从技能书提供法术链接，并用插件现有诊断或单独开发测试采集本人一次手动球的施法事件，再测试静滞存球/释放。区分主动施法 ID、治疗效果 ID、复制效果 ID，不以治疗跳数或法术名相同就认作一次手动施法。

确认前可先支持文字解析和视觉计划预览，但不能宣称实际施法自动确认已完成。未知 ID 应明确标未配置，不用占位假数字加入匹配表。

### 13.3 到点提醒与语音

- 时间轴中的球时间表示**开始施法**时间，不是球完成或治疗生效时间。
- 默认复用全局 `leadTime` 提前显示，以及现有多行 `AlertUI`，无需新造独立窗口。
- 例如计划 00:38 球，默认 00:35 开始显示倒计时；00:38 应开始球；计划 00:40 完成。
- 没有施法时按普通提醒规则过期，第一版不加入绿喷式“晚啦”持续纠错，不改变绿喷配额保护。
- `Voice.SKILL_FILES.BALL` 只有在真实音频文件存在时注册正确文件路径和时长；没有专用语音时明确仅视觉或使用现有可用的通用提示音，不能把不存在的 `ball.ogg` 当成功。
- 球语音沿用 owner 事件和现有队列。关闭/确认球时取消其排队语音，防止技能打完才播球；不要取消其他技能语音。
- 绿喷紧急纠错与普通球提示并发时，保留现有紧急提示优先级，不用普通球声音挡住“取消绿喷”。

### 13.4 关键问题：现有 0.9 秒关闭窗口小于球的 2 秒读条

**不能只把球 ID 加进 `SUCCEEDED_SKILLS` 就结束。**现有 `DismissActiveEvent` 按 `[time-leadTime, time+postHold]` 查找事件，而球按计划起手后 2 秒才完成，默认完成时已经超过 `postHold=0.9`。此外，球若开始后中断，也不能算成功。

建议增加小型普通施法匹配状态，独立于绿喷 token：

```text
PLANNED → CASTING（匹配手动起手，暂留提醒/可显示施法中）
CASTING → CONFIRMED（匹配成功事件，关闭提醒）
CASTING → PLANNED 或 MISSED（失败/中断，根据原计划窗口决定）
PLANNED → MISSED（没有起手且超过窗口）
```

建议实现：

1. 在 `CastTracker` 增加球的手动起手监听，实际使用的施法事件类型应经诊断确认；普通读条可从本人 `UNIT_SPELLCAST_START` 路径建立跟踪，不走绿喷的 EMPOWER 流程。
2. 起手时在未确认的 BALL 事件中，按实际开始与计划开始距离选最近候选；时间相同时用 sequence。第一版匹配窗口可复用 leadTime/postHold，另设参数时需要展示明确。
3. 建立 `activeBallCast={sessionGeneration,castGUID,castBarID,eventID,eventRef,startedAt}`。单条事件最多绑定一次，单次施法最多确认一条事件。
4. 起手只建立匹配，不能算次数、不能消耗绿喷 token。可以停止该球语音并显示“施法中”。
5. 匹配到实际成功回报才确认。即使此时已超过普通提醒窗口，也通过起手保存的 eventRef 关闭正确事件，而不是重新查附近时间。
6. `Timeline:Update` 对已绑定且尚在有效施法中的球不要按普通 0.9 秒规则直接过期；加单独的有限超时清理，防止丢失结束事件导致永远挂着。
7. 中断、失败清除绑定。如果仍在原窗口内，恢复未完成提示；否则标为错过。不要用通用 STOP 直接判失败：成功施法也可能伴随 STOP，需根据实测事件顺序区分。
8. 会话结束、换场、插件关闭时清理绑定和排队声音；异步回调必须检查 generation 和当前 snapshot，不能误关闭下一场同名事件。

可增加 `Timeline:MatchManualCast(skillKey, castStart, window)` 和 `Timeline:ConfirmManualCast(eventRef, identity, reason)`，并让球复用；这是拟新增接口。不要随意改变 `DismissActiveEvent` 的全局范围，导致其他技能提前关闭未来提醒。

若真实技能使用不同施法事件（如通道），应按实测添加相应适配，不能因为模型固定 2 秒就凭 `C_Timer.After(2)` 假定已成功。模型施法时间只用于计划，运行时确认由实际事件决定。

### 13.5 手动球与静滞复制球必须隔离

梦境织机输出的静滞内球是玩家真实手动球，需要提醒并消耗手动 CD。释放静滞复制出的球已经由 R 覆盖，**不再生成一条让玩家按的球提醒**。

成功确认优先依靠“已观察到的本人手动起手身份 → 对应成功回报”闭环，结合已验证的 ID。复制治疗/效果回报不能消费下一条手动 BALL 事件。

不要采用“释放静滞后的固定 2 秒内都忽略球”规则：玩家可能确实在释放同秒或紧接着手动打球，这样会漏报。也不要只依靠 `spellID == 球` 匹配，复制可能产生相似效果事件。

如果事件身份不可读取或无法可靠区分，只保持时间提示并记录“未确认”，不要猜测已经成功、不要改绿喷保护配额。沿用项目现有 `EC:IsSecret` 和受限值检查方法，不对不可安全读取的字段进行比较、拼接或日志转换。

第一版无需在线模拟绿喷剩余充能，也无需监听每个复制治疗跳数推算冷却。若未来加入实际偏差分析，手动球和复制球分别记账，每球只减一次，不能同时在成功事件和治疗日志两处重复减 CD。

### 13.6 与绿喷保护、配额、波次的关系

- BALL 不是 DREAM_BREATH token，不增加/消耗喷配额，不触发“先别喷”“绿喷晚啦”“取消绿喷”。
- 球不能调用 `AdvanceActualWave`；只有现有静滞开启逻辑负责波次变化。
- BYB 里的球只是两个喷之间的普通手动施法。两个喷仍各消耗一个原有喷 token，不能因中间有球就切断波次。
- 复制球不会消费喷 token；复制喷也不能被当作两次新的手动喷。
- 若扩 `CopyEvent` 增加 `castDuration/kind/generatedID` 等元数据，需要显式复制。当前函数按字段列出，并不会自动保留新字段。
- 新字段不可放进必须知道梦境织机的专用路径才生效；用户手写球的战术板同样应正常提醒。

### 13.7 建议验收用例

| 场景 | 预期 |
|---|---|
| 手写简单/MRT/法术 ID 的本人球 | 统一解析为 BALL 并显示 |
| 他人球或未知 ID | 不误加入本人提醒 |
| 计划 t=38，实际 t=38 起手、t=40 成功 | 精确确认该球，即使 postHold=0.9 |
| t=38 起手后中断 | 不确认成功；不消费喷配额 |
| 同一成功回报重复出现 | 最多关闭一条球事件一次 |
| 没有手动起手，只有静滞复制球效果 | 不关闭下一条手动球 |
| 释放静滞后立刻手动球 | 有可验证身份时正常确认，不能被时间屏蔽 |
| 提前/晚于匹配范围施放 | 不吞掉很远的未来计划，记录偏差或未匹配 |
| 前一场延迟成功回调落在下一场 | generation 不符，不确认新事件 |
| 无语音文件 | 视觉提醒正常，无不存在文件假成功 |
| 球与绿喷紧急纠错同时出现 | 球不覆盖纠错，也不改变喷额度 |
| BYB / BBY / BBF 计划 | 仅真实手动球有 BALL 提醒，BBF 没有复制球 |

第一阶段交付：文字/已验证 ID 识别、视觉提醒、可靠手动确认、复制隔离、语音队列取消、回归测试。专用球语音可以有明确的“未配置”状态；冷却感知、实时纠错、动态重排和实际收益统计可后续开发。
